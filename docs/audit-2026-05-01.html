P0Bugs critiques

À corriger avant toute refacto. Chaque fix est isolé et tient en quelques lignes.

1. Rate-limiting lyrics 1000× trop lent
MusicData.Infrastructure/Services/LyricsAggregator.cs:33,35

TimeSpan.FromSeconds(cfg.PerMilliSeconds) au lieu de FromMilliseconds. La config dit (10 req / 1000 ms) → effectif (10 req / 1000 s). À aligner sur MusicAggregator.cs:33.

2. Clé de rate-limit CoverArt incorrecte
MusicData.Infrastructure/ConfigureServices.cs:160

rateLimitOptions.ServiceLimits["covertart"] = …. Le dictionnaire est indexé par serviceType.Name.ToLowerInvariant() (MusicAggregator.cs:30). Le type est CoverArtService → clé attendue "coverartservice". CoverArt tombe donc dans le fallback (1 req / 1 ms) = pas de limite. Aligner les autres clés sur le pattern <typename>service.

3. Casse incohérente sur le HttpClient nommé lyricsOvh
MusicData.Infrastructure/ConfigureServices.cs:121 ↔ Services/LyricsOvh/LyricsOvhService.cs:10

Enregistré "lyricsOvh" et injecté [FromKeyedServices("lyricsovh")]. À uniformiser (de toute façon [FromKeyedServices] est redondant avec AddHttpClient<TImpl>(name) qui passe déjà l'HttpClient typé — voir P2-7).

4. Le mapper artiste perd des champs au cache
MusicData.Application/Mappers/ArtistMapper.cs:15-84 + MusicData.Domain/Entities/ArtistEntity.cs

ArtistMapper ne mappe pas Wikipedia, et ArtistEntity n'a pas TikTok / Threads / SongKick / SoundCloud / Imdb / Fanart4Url / Fanart5Url alors que ArtistDto les expose. Cycle : 1ʳᵉ requête → DTO complet ; entité persistée tronquée ; 2ᵉ requête → cache hit → DTO appauvri. Le cache abîme silencieusement les données.

5. EnsureIndex(unique: true) sur ArtistEntity.Name
MusicData.Infrastructure/Repositories/ArtistRepository.cs:15

Deux artistes peuvent légitimement avoir le même nom (homonymes / artistes locaux/nationaux) et MusicBrainz les distingue par MBID. La contrainte unique sur Name jettera à l'insertion. Garder unique uniquement sur MusicBrainzID.

6. StringComparison.InvariantCultureIgnoreCase dans les expressions LiteDB
ArtistRepository.cs:25,27,52,58 · AlbumRepository.cs:27,29,54,60-61 · LyricsRepository.cs:24-25,50-51

LiteDB traduit ces expressions en BSON queries et n'honore pas l'enum StringComparison — c'est ignoré ou rendu en comparaison ordinale. Corriger via BsonExpression.Create("LOWER($.Field) = @0", value.ToLowerInvariant()) ou normaliser à l'écriture (champ NameLower).

7. Race condition cache-aside
Tous les handlers Get* (Application/Features/...)

Séquence repo.Get → aggregator.Get → repo.Add non atomique. Deux requêtes concurrentes sur le même artiste inconnu déclenchent 2 appels externes complets puis 2 inserts (dont un échouera ou écrasera l'autre). Court terme : verrou par clé via ConcurrentDictionary<string, SemaphoreSlim>. Plus long terme : IMemoryCache/single-flight.

P1Architecture & duplication

1. Les 4 feature handlers sont du copier-coller

GetArtistByName, GetArtistByMusicBrainzId, GetAlbumByName, GetAlbumByMusicBrainzId (et largement GetLyrics) implémentent exactement le même squelette. Remplacer par un CachedReadHandler<TKey, TDto, TEntity> paramétré par 3 délégués (lookup cache, fetch externe, persistance). Diminuera ~200 lignes et garantira cohérence métriques/logs.

2. Les 2 aggregators sont 90 % identiques

MusicAggregator et LyricsAggregator partagent la construction du dictionnaire de TokenBucketRateLimiter, le pattern Safe*Async. Extraire une classe de base RateLimitedAggregator<TService> ou un helper RateLimitedRunner.

3. La merge-logic BuildMergedArtist/BuildMergedAlbum est artisanale et fragile
MusicAggregator.cs:184-281

~30 champs énumérés à la main avec FirstNonEmpty / FirstGreaterThanZero. Tout nouveau champ DTO doit être ajouté ici sinon il est silencieusement perdu (cf. P0-4). Soit Source Generator, soit merge réflexif MergeStrings(items, dto => dto.X).

4. Layering cassé : Domain dépend de LiteDB
MusicData.Domain/MusicData.Domain.csproj:10

Référence LiteDB. Le domaine ne devrait pas connaître la persistance. Aucune des entités n'utilise d'attribut LiteDB — la dépendance peut probablement être supprimée et déplacée dans Infrastructure.

5. Fuite d'abstraction dans MusicAggregator
MusicAggregator.cs:45,115

_services.OfType<MusicBrainzService>().FirstOrDefault()! — l'aggregator connaît la classe concrète d'un service. Le rôle "résoudre nom→MBID" mérite sa propre interface IMusicBrainzLookup. Sinon impossible de tester / remplacer MusicBrainz, et risque de NRE.

6. Code mort à supprimer
  • MusicData.Api/Endpoints/HealthEndpoints.cs (classe HealthEndpoints2, jamais appelée)
  • MusicData.Application/Interfaces/IDataContext.cs (interface vide)
  • MusicData.Infrastructure/LiteDataContext.cs (ni enregistrée ni résolue)
  • MusicData.Infrastructure/Utilities/ObjectDumper.cs (aucun usage)
  • MusicData.Shared/Requests/GetArtistRequest.cs (aucun usage)
  • Méthodes Update/Delete des trois repositories : aucun appelant
  • MusicData.Shared/Responses/ : dossier vide
  • MusicDataApi/Dockerfile.original
7. Endpoints : duplication transversale

Les 5 Map* répètent : validation longueurs (255/36), RequireAuthorization/RequireRateLimiting, démarrage d'Activity, headers Cache-Control/Vary. Extraire MapGetCached(...) + IEndpointFilter pour les bornes. L'Activity manuelle peut être déléguée à AddAspNetCoreInstrumentation.

8. Configuration HTTP client : 6× le même bloc
Infrastructure/ConfigureServices.cs:59-149

Extraire services.AddExternalHttpClient<IService, TImpl, TSettings>("name") qui fait BaseAddress, Timeout, UA, decompression et binding IOptions<TSettings> en une ligne.

9. RateLimitOptions codé en dur dans AddServices
ConfigureServices.cs:154-164

Les seuils sont hard-codés en C# alors qu'on a déjà IConfiguration. Déplacer sous Services:<name>:RateLimit et binder via Configure<RateLimitOptions>.

10. _concurrencySemaphore static avec un état d'instance

Sur MusicBrainz volontaire (single-flight global), sur LastFm/Fanart probablement pas voulu (capa = 5). De plus, ce verrou fait doublon avec le TokenBucketRateLimiter côté aggregator. Choisir : 1 mécanisme par dimension (concurrence vs débit).

P2Clean code

1. Origin est une string libre

Valeurs : "Cache" | "Aggregated" | "NotFound" | "LyricsOvh" | …. Remplacer par un enum DataOrigin sérialisé en string.

2. DTO/Entity divergent silencieusement

Au-delà de l'ArtistMapper, AlbumDto et AlbumEntity ne sont pas symétriques. Test de mapping round-trip Dto→Entity→Dto qui échoue dès qu'un champ n'est pas symétrique.

3. Les 3 repositories partagent un pattern Add quasi identique

Logique "find existing → upsert avec UpdateDateTime/Version" répétée. Base LiteDbRepository<TEntity> avec une méthode abstraite FindExisting(TEntity).

4. Domain entities polluées par champs inutilisés

ArtistEntity.BiographyFR / FanartsCount / PicturesCount / LogosCount / BannersCount / BornYear ; AlbumEntity.CoversCount : aucune écriture/lecture.

5. Public statics mutables dans Levenshtein

Levenshtein.IgnoreCase est public static et mutable. Risque de contamination entre tests/threads. t.Substring(j-1,1) == s.Substring(i-1,1) peut être t[j-1] == s[i-1].

6. Telemetry en static — testable seulement via état global

OK pour l'usage actuel, mais bascule sur IMeterFactory nécessaire pour des assertions en test.

7. Combinaison AddHttpClient<TImpl>(name) + [FromKeyedServices(name)] HttpClient

Redondant. Le client typé reçoit déjà son HttpClient via ITypedHttpClientFactory. Soit retirer l'attribut, soit utiliser AddHttpClient(name).AddTypedClient<>() explicitement.

8. EnsureIndex à chaque résolution de scope

Repositories scoped → EnsureIndex appelé à chaque requête HTTP. Idempotent mais inutile. Faire un IndexInitializer IHostedService au démarrage.

9. Coquilles & noms approximatifs
  • IMusicAggregator.GetAlbumByMusicBrainzIdsync (au lieu de …IdAsync)
  • Clé HttpClient "covertart" (typo) — ConfigureServices.cs:106
  • Classe HealthEndpoints2
  • LyricsOvhRootobject (camelcase étrange)
10. Enabled dupliqué partout

Chaque service a public bool Enabled { get; set; } = settings.Value.Enabled; et if (!Enabled) return null;. Soit ne pas enregistrer le service du tout quand Enabled=false (idéal), soit retirer la propriété.

11. Fanart.FanartImage.Score recalculé sur chaque accès

Parse de Likes à chaque getter. Préférer un champ calculé une fois.

12. appsettings.Development.json versionne des clés réelles

LastFm, Fanart, New Relic insert key, ApiKey serveur, et MusicDataApi.http contient une autre clé. Tout déplacer dans User Secrets et faire tourner les clés exposées.

13. MusicData.Shared.csproj réfère MusicData.Domain

Brouille la sémantique (un projet "Shared" devrait être feuille). Soit fusionner Shared dans Application, soit déplacer ce qui dépend de Domain hors de Shared.

14. app.UseAuthorization() appelé sans middleware d'erreur
Program.cs:55-58

Pas de UseExceptionHandler ni de ProblemDetails → 500 "blanc" en cas d'exception non gérée. Ajouter app.UseExceptionHandler() + services.AddProblemDetails().

15. services.AddAuthorization() deux fois
Infrastructure/ConfigureServices.cs:228-237

Un AddAuthorization(o => …) puis un AddAuthorization() nu juste après. Le second est inutile.

16. Pas de tests

Pas de projet *.Tests. Les bugs P0-1, P0-2, P0-4 auraient été pris par un seul test d'intégration end-to-end "round-trip cache".

Plan d'attaque suggéré

  1. PR "P0" — fixe les 7 bugs critiques. Indépendants les uns des autres, ≤ 5 lignes chacun.
  2. PR "ménage" — supprime tout le code mort de P1-6 + P2-9 (~ 6 fichiers + 1 dépendance LiteDB).
  3. PR "DRY handlers" — extrait CachedReadHandler<…> (P1-1) et l'AddExternalHttpClient helper (P1-8). Plus gros gain de lisibilité avec peu de risque.
  4. PR "tests" — projet xUnit + 1 test par feature handler en mockant l'aggregator + 1 test de round-trip mapper. Sans ça, les futurs ajouts de champs DTO continueront de pourrir le cache silencieusement.
  5. Le reste (P1-3 merge réflexif, P1-9 config externalisée, P2 divers) au rythme des features.
